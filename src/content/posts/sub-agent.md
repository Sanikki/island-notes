> **大侠追一个 Bug，追着追着翻了 30 个文件，聊了 60 轮。回头一看，**最初要修什么来着？
>
> 江湖经验：修 Bug 的时候，高手都会**另开一个终端**去追踪调用链。查完了，终端一关，结论记在纸上，回到原来的终端继续修。
>
> **子 Agent，就是那个“新终端”。给它一个干净的脑袋（上下文），派它去干一件独立的事，干完了只把结论带回来，中间怎么想的、走了哪些弯路，全部一笔勾销。** 主 Agent 的脑袋（上下文）始终干干净净。
>
> Sub-Agent就像是一个函数一样，主Agent将参数（上下文）传给他，Sub-Agent将结果传回。
>

## Sub-agent 解决什么问题？
| 症状 | 病因 | Sub-agent 解药 |
| :--- | :--- | :--- |
| 主 Agent 越聊越健忘 | messages 列表涨到 120 条，中间过程占满窗口 | 子 Agent 用**全新 messages[]**，干完就扔 |
| 修 Bug 时被“调用链”带偏 | 注意力在中间过程上漂移，忘了最终目标 | 子 Agent 只回传结论，中间过程不污染主对话 |
| 大文件读到一半，上下文爆了 | 读文件把窗口撑满 | 子 Agent 爆了也不影响主 Agent |


> **一句口诀：大任务拆小，每块都是干净脑。****主脑只管收结论****，中间内耗全不要。**
>

## 隔离靠哪几点实现？
> **上下文隔离、工具集隔离、生命周期隔离、文件系统共享、四重隔离，层层封锁，没有一道是虚的。**
>

### ① 上下文隔离
子 Agent 启动时，代码直接给了一个 **全新的 **`messages = []`：

```python
messages = [{"role": "user", "content": description}]  # 就这一句，干净得跟白纸一样
```

主 Agent 的 120 条历史记录，它一条都看不见。它只知道你派给它的那一句话：“去查一下这个项目用的啥测试框架。”

### ② 工具集隔离
主 Agent 有 6 件兵器，子 Agent 只拿到其中 **5 件**：

```python
sub_tools = [bash, read_file, write_file, edit_file, glob]  # 没有 task！
```

**没有 **`task`** 工具 = 不能递归 spawn 新的子 Agent。** 防止“子 Agent 又生孙子 Agent”的无限套娃。

### ③ 生命周期隔离
```python
for _ in range(30):   # 最多 30 轮，防止死循环
    ...
# 循环结束 → 只取最后一句文本 → 子 Agent 对象销毁
```

它不是一个常驻的“小弟”，而是一个**用完即焚的“临时工”**。干完活，内存一释放，干干净净。

### ④ 文件系统共享
注意：**上下文隔离 ≠ 权限隔离。**

子 Agent 写的文件、改的文件，**留在工作目录里**。主 Agent 能看见，因为这是物理磁盘上的变化。但子 Agent 的内心独白（推理过程）主 Agent 永远看不见。

> **口诀：物理文件可共享，内心独白全烧光。手里没拿递归令，三十回合必收场。**
>

## 为什么子 Agent 只能拿工具子集？
**① 防递归（禁止套娃）**  
如果子 Agent 也有 `task` 工具，它可能再 spawn 一个“孙 Agent”。孙 Agent 再 spawn 一个“曾孙 Agent”……**最后变成无限套娃，栈溢出。**

教学版的做法最干脆：**子 Agent 的工具列表里，根本没有 **`task`** 这一项。** 它想 spawn 也没法 spawn。

**② ****聚焦****（少即是多）**  
工具越多，模型的选择空间越大，**出错的概率也越大**。给子 Agent 只配 `read` 和 `grep`，它就只能“读文件”和“找文件”——行为收敛，结果可控。

**③ 安全（权限不该自动继承）**  
上下文隔离不自动意味着权限隔离。子 Agent 如果继承了主 Agent 的全部工具，可能会：

+ 删除不该删的文件
+ 执行不该执行的命令
+ 访问不该访问的网络

> 子 Agent 的工具集，必须显式、逐个审批。给的越少，越安全。
>

## 子 Agent 该返回什么？
> **“只送结论，不送过程。只给结果，不给草稿。”**
>

```python
# 子 Agent 跑完 30 轮后
return extract_text(messages[-1]["content"])  # 只取最后一条消息的文本
```

它返回的是：

+ ✅ 提炼后的结论：“这个项目用的是 pytest，配置文件在 `pyproject.toml` 里。”

它不返回的是：

+ ❌ 它读过的 10 个文件的内容
+ ❌ 它执行过的 15 条命令的输出
+ ❌ 它思考的 20 轮推理过程
+ ❌ 整个 `messages[]` 列表

> **江湖类比：** 你派探子去查一个案子。探子回来只报告：“凶手是张三，在城西客栈。”——你不会要求他把沿途看过的每一棵树、问过的每一个人都背一遍给你听。
>

## 什么任务适合开 Sub-agent？
✅ 适合开 Sub-agent 的特征：

1. **独立可并行**：三篇文档各不相干，三个人同时读。
2. **有明确边界**：“查一下这个项目的测试框架” vs “写一个完整的新功能”。
3. **失败可接受**：子 Agent 崩了，主 Agent 还能继续。
4. **不需要主 Agent 中途决策**：主 Agent 只等最终结果。

❌ 不适合开 Sub-agent 的特征：

1. **需要主 Agent 反复决策**：子 Agent 每走一步都得回头问“这样行不行”——频繁通信反而更慢。
2. **结果必须精准结构化**：子 Agent 的输出要是 JSON，LLM 容易抽风。
3. **子任务太小**：开一个 Agent 的代价（网络请求、Token 消耗）比直接干还大——杀鸡用牛刀。

### 战例：“读三篇文档总结共同主题”
```plain
主 Agent 收到指令
  │
  ├─→ 开子 Agent A → 读 doc1 → 返回 200 字摘要
  ├─→ 开子 Agent B → 读 doc2 → 返回 200 字摘要
  └─→ 开子 Agent C → 读 doc3 → 返回 200 字摘要
  │
  ▼
主 Agent 拿到三份摘要 → 上下文只有 600 字 → 轻松总结共同主题
```

### 为什么这个任务适合？
1. **三篇文档互不依赖**，可以并行
2. **每篇文档有明确边界**（只读这一篇）
3. **失败一个不影响其他**（doc2 读不了，doc1 和 doc3 继续）
4. **主 Agent 不需要中途介入**（等着收结论就行）

## 一句话归档
> **Sub-agent = 新终端 + 干净脑 + 限制工具 + 只回结论。隔离的不是文件，是上下文。工具少不是残废，是专注。** 🏔️
>

### 📋 Sub-Agent 隔离与治理决策表
| 优先级 | 决策 | 选择 | 原因 | 如果不使用这种决策，会出现什么问题 |
| --- | --- | --- | --- | --- |
| **P0** | **上下文隔离** | 全新 `messages[]` | 子 Agent 的中间过程不污染主 Agent 的上下文 | 如果不只传回结论，可能会导致传回无用信息（如检索到的原文噪音、失败的尝试记录），挤爆主 Agent 的上下文窗口，并干扰其综合判断。 |
| | **安全策略不跳过** | 子 Agent 工具调用也走 `PreToolUse` hook | 上下文隔离不代表权限隔离 | 如果跳过子 Agent 的安全钩子校验，攻击者可能通过子 Agent 间接发起非法工具调用（如 `shell_exec`、`file_delete`），绕过主 Agent 的权限管控，造成严重的数据泄露或系统破坏。 |
| | **强制超时熔断** | 子 Agent 执行设置硬超时（如 30s），超时直接返回空或错误状态 | 防止单篇文档读取或外部 API 卡死，将故障隔离在单个子任务内 | 如果不设超时，遇到外部依赖阻塞时，主 Agent 会**无限期挂起等待**，导致工作流线程池被耗尽，所有用户请求集体超时，引发级联雪崩。 |
| | **返回前 Schema 校验** | 在子 Agent 输出最终 JSON 前，强制校验必填字段（如 `core_answer`）是否存在且非空 | 防止子 Agent 因幻觉输出空对象或非标准格式，导致主 Agent 解析层直接崩溃 | 如果不做格式校验，子 Agent 可能返回 `{"思考": "我读完了"}` 这种纯文本字典，主 Agent 尝试取 `core_answer` 字段时直接抛 `KeyError` 或解析异常，导致交互中断。 |
| **P1** | **只回传结论** | `extract_text(last_message)` | 不是回传整个 `messages` 列表 | 如果回传整个 messages 列表，主 Agent 会看到子 Agent 的内部推理链（CoT）、工具调用日志及中间报错，导致主 Agent “想太多”或被虚假错误信息误导，最终答非所问。 |
| | **禁止递归** | 子 Agent 无 `task` 工具 | 防止子 Agent 再 spawn 新的子 Agent | 如果不禁用（即子 Agent 拥有派发任务权限），可能引发无限递归或指数级任务扩散（如子 Agent 为解决一个小问题再生成 5 个孙 Agent），导致任务永远无法结束，Token 消耗失控。 |
| | **任务粒度控制** | 小任务（如翻译一句话、算个加减法）由主 Agent 直接处理，**不创建**子 Agent | 子 Agent 的启动开销极大（状态初始化、Prompt 加载、连接池占用），大炮打蚊子得不偿失 | 如果任何任务都无脑起子 Agent，高频轻量请求的响应时间会从 **50ms 飙升至 2s+**，系统吞吐量呈指数级下降，GPU 资源被无效调度占满。 |
| | **工具集精简（最小权限）** | 仅挂载当前任务必需的 tools（如仅挂载 `read_pdf`），剔除搜索/计算等无关工具 | 减少子 Agent 的决策空间，既能降低 Token 消耗，又能防止误操作 | 如果给子 Agent 挂载了全量工具，它可能在文档里找不到答案时，**擅自调用浏览器搜索或执行系统命令**来“曲线救国”，既浪费大量 Token，又极易产生失控的幻觉输出。 |
| | **错误隔音与降级** | 子 Agent 抛异常时 `catch` 住，返回标准化 `{"error": "xxx"}` JSON，主 Agent 走 Fallback 逻辑 | 一个子 Agent 读崩了，不影响其他并行的子 Agent 结果，也不中断主流程 | 如果子 Agent 直接往上抛异常，3 个任务中任意一个读崩（如文件损坏），会导致**整个主流程直接中断**，用户什么回答都收不到，且难以定位具体是哪个环节出了问题。 |

### 🚦 分级实施策略速查
| 优先级 | 定位 | 实施方式 | 失败后果 |
| --- | --- | --- | --- |
| **P0** | **系统红线** | 写在 **Orchestrator 编排代码**中，Sub-Agent 无法绕过 | **生产事故**（服务崩溃/安全漏洞/数据泄露） |
| **P1** | **工程优化** | 写在 **System Prompt 顶层指令** + **日志监控告警** | **性能劣化**（耗时增加/费用飙升/偶发幻觉） |


---

### 💡 上线前检查建议
按 P0 → P1 的顺序依次确认，P0 项**全部通过**才允许上线：

+ **P0-1** 主 Agent 传给子 Agent 的是否是全新的空 `messages[]`（而非克隆历史）？
+ **P0-2** 子 Agent 的工具调用是否被 `PreToolUse` 钩子拦截校验？
+ **P0-3** 子 Agent 执行是否有硬超时拦截器（`asyncio.timeout` 或 `threading.Timer`）？
+ **P0-4** 子 Agent 输出后是否有 JSON Schema 校验器检查必填字段？
+ **P1-1 ~ P1-5** 子 Agent 的 System Prompt 是否包含了"禁止递归"、"不要输出推理链"、"小任务禁止创建子任务"等指令？
